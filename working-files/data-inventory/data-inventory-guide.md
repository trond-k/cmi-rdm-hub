# Map your project's data in 30 minutes

Use this guide early, before the project hardens around vague assumptions. The goal is not a full data management plan. It is a first operational picture of your data landscape: what data the project will create, receive, move, and need to govern.

The output is a rough inventory. It does not need to be polished. It needs to exist.

## Step 1. List what you will generate

Think method by method. Interviews produce recordings, transcripts, and notes. Surveys produce response data. Observation produces field notes, photographs, or video. For each item, note:

- what it is
- who it concerns
- rough volume

Include the supporting material people forget: contact lists, consent records, correspondence with participants, translation files, and anonymisation keys.

## Step 2. List what you will receive or reuse

Now add the data that already exists:

- administrative or registry data
- partner-generated data
- prior project data
- archives and document collections
- external datasets you plan to reuse

For each item, note where it comes from, whether access is open or conditional, and whether it may include identifiable people.

## Step 3. Trace where data moves

Ask who handles each data stream and where it goes next.

This is where many projects discover the real governance questions:

- assistants collecting in the field
- partners holding working copies
- transcription or translation services
- cloud tools used during analysis
- transfers across institutions or countries

You do not need a formal diagram. A rough list of movements is enough.

## Step 4. Ask the governance questions

For each data stream, ask:

- Will this involve personal data or contextual sensitivity?
- Who will handle it, and under what arrangements?
- Will it cross institutional or national boundaries?
- What can realistically be shared later?
- What is still unresolved?

At this stage you are not solving every issue. You are making the issues visible.

## Check what you may have missed

Researchers often miss the implicit data objects rather than the obvious ones. Common misses include:

- the key linking pseudonyms to identities
- pilot data that never made it into the "real" dataset
- codebooks, README files, and translation notes
- sampling frames and recruitment lists
- files shared temporarily with assistants, partners, or service providers

## What to do next

Turn the rough inventory into something you can actually use:

- If you need a research-question-based worksheet, use the [Data Needs Matrix](../templates-and-checklists/data-needs-matrix.md).
- If you need to decide whether people are identifiable, use [Decide whether your project uses personal data](personal-data-guide.md).
- If you need to decide where the different files should live and who should access them, use [Choose storage and control access](storage-and-access.md).
- If you need to turn the inventory into a working plan, use [Write a working data management plan](working-dmp.md).
- If you need to tighten project setup, use [Set up your project data workflow](project-data-workflow.md).

## The minimum before you move on

Before you move beyond early scoping, you should be able to confirm:

- [ ] you have listed the main data types, sources, and methods
- [ ] you have noted whether personal data or contextual sensitivity is likely
- [ ] you have identified who else will handle data
- [ ] you have noted any cross-border data flows
- [ ] you have not promised sharing the project cannot deliver
- [ ] you know which questions still need answers in planning
