# How to share and collaborate in Microsoft 365 at CMI

## Purpose

This page explains how CMI staff should share and collaborate on files in Microsoft 365, especially in OneDrive, SharePoint, and Teams.

The aim is not simply to make sharing easy. It is to make sharing proportionate, controlled, and appropriate to the kind of research material involved.

At CMI, this matters because research projects often involve:

* international collaborators
* commissioned or contract-based work
* qualitative material and long-tail research data
* personal data and other confidential information
* files that need to remain accessible beyond one individual staff member

Microsoft 365 can support collaboration well, but only if staff choose the right location, the right sharing method, and the right access level.

---

## Core rule

Share only with the people who actually need access, and only at the level they need.

In practice, this means:

* do not use the broadest link setting by default
* do not give edit access when view access is enough
* do not keep project-critical shared files only in a personal OneDrive
* do not share folders unless everything in the folder is appropriate for the same audience
* review and remove access when collaboration changes

Microsoft supports several link types and permission models in OneDrive and SharePoint, including direct access, “Specific people” links, organization-wide links, and—if enabled by administrators—“Anyone” links. “Specific people” links are non-transferable and tied to the named recipients, while broader links are less controlled. ([Microsoft Learn][1])

## Before you share: choose the right place

### Use OneDrive when

Use OneDrive for:

* your own working files
* short-term collaboration on files you currently manage
* limited sharing with clearly identified individuals

Microsoft’s sharing model for OneDrive is built around files that are private until the owner shares them. ([Microsoft Support][2])

At CMI, OneDrive is usually suitable for:

* early drafting
* ad hoc collaboration with a small number of colleagues
* temporary file exchange

It is usually not the best place for core project documentation or shared project datasets that should outlast one individual’s role.

### Use SharePoint or Teams when

Use SharePoint or Teams when:

* the material belongs to a project, team, or unit rather than one person
* several people need stable, ongoing access
* files should remain available if a staff member leaves or changes role
* the collaboration space needs clearer group ownership

Files shared in Teams channels are stored in SharePoint, and Teams-connected files are part of the wider SharePoint permission structure. Standard channels use the main team site; private channels use separate SharePoint sites. Files shared in private Teams chats are typically stored in the sender’s OneDrive. ([Microsoft Learn][3])

At CMI, this means:

* use Teams/SharePoint for active project spaces
* do not assume a file is “just in Teams”
* remember that chat-shared files and channel-shared files are not stored in the same place

---

## Recommended default for CMI

For most ordinary internal collaboration, the safest default is:

1. store the file in the correct project or team location
2. share with named people
3. give view access unless edit access is needed
4. avoid broad reusable links unless there is a clear reason

This fits both Microsoft’s permission structure and CMI’s general need for access minimisation.

---

## Sharing options: what to use and what to avoid

### Preferred: direct access or “Specific people”

Where possible, share with named people or use a “Specific people” link.

Why this is preferable:

* it is clearer who has access
* it is easier to review later
* it is less likely to be forwarded informally
* external recipients authenticate as guests when required
* access is more auditable than broad anonymous sharing

Microsoft states that “Specific people” links work only for the people specified by the sender and are revocable. Microsoft also notes that authenticated guest-based sharing is more trackable than anonymous sharing. ([Microsoft Learn][1])

At CMI, this should normally be the default for:

* project documents
* draft reports
* collaboration with named external partners
* research administration files
* any file containing personal data or confidential content, unless the platform itself is not appropriate for that material

### Use with caution: “People in your organization”

An organization-wide link may be useful for internal reference documents that are meant to circulate within CMI.

It is usually not appropriate for:

* restricted project material
* confidential commissioned work
* data files
* documents that only a subset of staff should see

Microsoft notes that “People in your organization” links work for anyone inside the organization. ([Microsoft Learn][4])

At CMI, use this only when internal broad visibility is genuinely intended.

### Usually avoid: “Anyone with the link”

“Anyone” links allow access to anyone who has the link, including people outside the organization, without sign-in in many cases. Microsoft notes that these links cannot be audited in the same way as authenticated access. ([Microsoft Learn][4])

For a research institute like CMI, this should usually not be the default.

In most research and administrative contexts, avoid “Anyone” links for:

* project material
* draft outputs
* partner documents
* personal data
* confidential or contract-restricted material

They may be acceptable for deliberately low-risk material intended for broad circulation, but not for normal project sharing.

## Edit or view?

### Give edit access only when needed

Edit access is for people who are actively working on the file.

View access is for people who need to read, check, or follow the document but not change it.

Microsoft’s OneDrive and SharePoint sharing settings allow you to grant edit access or remove editing permission. ([Microsoft Support][2])

At CMI, a useful rule is:

* project core team: edit if needed
* supervisors, advisers, administration, or occasional collaborators: often view only
* external recipients: start with view only unless there is a clear collaboration need

This is especially relevant in research projects where version control, attribution, and documentation matter.

---

## File sharing versus folder sharing

### Share files when possible

File-level sharing is often better than folder-level sharing.

It gives more precise control and reduces accidental over-sharing.

### Share folders only when the whole folder has the same audience

Microsoft allows folder sharing in OneDrive and SharePoint, but sharing a folder means sharing everything inside it according to those permissions. ([Microsoft Support][2])

At CMI, do not share a folder if it contains a mixture of:

* notes
* transcripts
* administrative files
* draft publications
* personal data
* dissemination material

Instead:

* reorganize first
* separate files by purpose or sensitivity
* then share the correct folder or subfolder

This is particularly important in qualitative projects, commissioned research, and projects with multiple external partners.

## Working in Teams

Teams is useful for day-to-day collaboration, but it can hide where files actually live.

Key points:

* channel files are stored in SharePoint
* private chat files are stored in OneDrive
* permissions follow the underlying storage location and membership structure

Microsoft documents this Teams/SharePoint/OneDrive integration clearly. ([Microsoft Learn][3])

At CMI, this means:

* use Teams for collaboration and communication
* do not rely on Teams alone as your mental model of file ownership
* check whether the file is in a project-owned SharePoint space or someone’s personal OneDrive

For project continuity, core shared material should normally sit in a project/team space, not only in chat-based sharing.

## Sharing with external collaborators

CMI projects often involve partners outside CMI. Microsoft 365 supports this, but external sharing should be deliberate.

Microsoft allows external or guest sharing in OneDrive and SharePoint, subject to organization and site settings. Site-level and organization-level defaults can also control link types, guest expiration, and whether broader sharing is available. ([Microsoft Learn][5])

### For CMI, external sharing should follow these principles

Use ordinary MS365 sharing only when:

* the collaboration requires it
* the material is appropriate for the platform
* access can be limited to named people where possible
* there is no contractual, ethical, legal, or security reason to use a different solution

Be especially careful when the material involves:

* personal data
* confidential field material
* sensitive qualitative data
* unpublished partner-provided data
* files governed by contractual restrictions
* international collaborations where legal and organizational obligations may be more complex

In those cases, the question is not only “Can this be shared in MS365?” but also “Should it be?”

At CMI, where researchers often work across jurisdictions and with external partners, platform convenience should not override project-specific obligations.

## Use link settings actively

When you share, do not just paste the default link.

Check the link settings and adjust them.

Depending on your CMI configuration, Microsoft may allow options such as:

* specific people
* people in your organization
* anyone with the link
* allow editing / remove editing
* expiration dates
* block download for view-only sharing

Microsoft’s support documentation explicitly notes expiration options and block download options for supported OneDrive/SharePoint sharing scenarios. ([Microsoft Support][2])

### Good CMI practice

For most non-public sharing:

* change the link from the broadest available option to the narrowest appropriate one
* remove edit permission unless editing is needed
* use expiry where the access is temporary
* consider block download for view-only reference sharing when appropriate and available

Block download is helpful for reducing casual redistribution, but it is not a substitute for proper platform choice or proper access control. Microsoft also notes that existing edit permissions can still allow downloading. ([Microsoft Support][6])

---

## Manage and remove access

Sharing should not be permanent by accident.

Microsoft allows file owners to review and change permissions, remove people, and delete sharing links through the Manage Access interface in OneDrive and SharePoint. ([Microsoft Support][7])

At CMI, access should be reviewed when:

* a collaborator leaves the project
* a contract ends
* a report is delivered
* a student assistant finishes work
* data collection closes
* project roles change

This is especially important for projects with external collaborators and for ad hoc sharing that accumulates over time.

## CMI-specific practical guidance

### 1. Do not use personal OneDrive as the long-term home of project-critical material

If a file is central to a project, move it into a shared project space.

This matters for:

* continuity
* handover
* accountability
* later review of access

### 2. Separate files before sharing

Do not build one mixed project folder and then try to solve everything with permissions.

Instead:

* separate working drafts
* separate administrative records
* separate data files
* separate outputs for external circulation

### 3. Default to named recipients

For most CMI research collaboration, named access is better than open link circulation.

### 4. Treat external sharing as a governance issue, not just a technical action

Before sharing externally, consider:

* what kind of material this is
* whether the recipient really needs access
* whether they need edit or only view
* whether MS365 is the right environment for this material at all

### 5. If unsure about sensitivity, ask

CMI is still developing more formal data-classification practices. Until classification is fully formalized, staff should seek advice when unsure whether material is too sensitive for ordinary sharing.

## Quick decision guide

### Use OneDrive when

* you own the file
* collaboration is limited
* access is temporary or narrow
* the file does not need project-level ownership

### Use SharePoint/Teams when

* the file belongs to a project or group
* several people need continuing access
* the file should remain accessible beyond one person
* the collaboration is ongoing

### Use “Specific people” or direct access when

* access should be limited
* the recipients are known
* the file is project-related, confidential, or non-public

### Use view-only when

* recipients only need to read
* you want to reduce accidental changes
* the file is a reference, review, or sign-off document

### Avoid broad links when

* the file is not intended for wide circulation
* the material is confidential
* the file contains personal data
* the project has contractual or ethical restrictions
