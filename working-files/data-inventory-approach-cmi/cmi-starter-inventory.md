# The CMI starter inventory

Most CMI projects should start with a small inventory. The starter inventory has twelve fields. It is enough to identify each data object, understand its context, assign responsibility, assess basic risk, locate the authoritative copy, control access, and plan what happens next.

Use one row per data object. A data object can be a category of material, not an individual file.

## The twelve starter fields

| Field | What to write | Why it matters |
| --- | --- | --- |
| Data object name | Short, recognisable label | Lets people know what row they are looking at |
| Short description | What the object contains | Makes the object understandable without opening files |
| Data type or material | Interview, survey, fieldnotes, admin data, code, consent records, documentation, etc. | Helps connect the object to relevant guidance |
| Source or method | Created by the project, collected from public sources, received from a partner, derived from another object | Clarifies origin, responsibility, and restrictions |
| Project context | Work package, country, partner, article, field site, project phase, or method context | Preserves meaning and helps assess contextual risk |
| Responsible role | PI, project manager, research assistant, partner field lead, data adviser, etc. | Makes accountability visible |
| Personal data and sensitivity | No personal data, personal data, special category data, politically/contextually sensitive, confidential, unknown | Signals GDPR, ethics, and security needs |
| Legal, Sikt, or restriction note | Consent, Sikt reference, data agreement, ethics condition, contractual limit, or "not applicable" | Links the object to obligations that affect use |
| Storage location | System, folder, repository, or storage environment where the authoritative copy lives | Prevents uncertainty about where data are held |
| Access | Who can access it and under what conditions | Supports access control and handover |
| Status | Planned, live, processing, ready for review, archived, deleted, retained, or to be reviewed | Shows where the object is in its lifecycle |
| Retention or end state | Delete, retain internally, archive, restrict, share, transfer, review later | Supports closure, archiving, deletion, and sharing decisions |

## Suggested status values

Status does not need to be elaborate. Use values that help the project act:

| Status | Use when |
| --- | --- |
| Planned | The object is expected but does not yet exist |
| Live | The object exists and is actively used or collected |
| Processing | The object is being cleaned, transcribed, translated, coded, anonymised, or transformed |
| Ready for review | A decision is needed before sharing, archiving, deletion, or wider access |
| Archived | The object has been deposited or stored for long-term retention |
| Deleted | The object has been deleted according to plan |
| Retained | The object is kept internally after active use |
| To be reviewed | Something important is unknown or unresolved |

## How much detail is enough?

Each field should be specific enough to support action. "SharePoint" may be too vague if several project folders exist. "Restricted project folder / interviews / audio" may be enough if only approved users can access it.

"Personal data" may be enough for a first sketch. Before collection, the project may need to distinguish direct identifiers, voice, location, special category data, or contextual identifiability.

"To be reviewed" is acceptable when something is genuinely uncertain. Do not leave important uncertainty hidden in blank cells.

## Key idea

Start with the twelve fields. Add more detail only when a decision, risk, agreement, funder requirement, or project handover need makes it necessary.
