# What is a data inventory?

A data inventory is a working overview of the data objects in a research project. It records what data exist or are expected, where they are stored, who is responsible for them, what risks or restrictions apply, and what should happen to them over time.

The inventory helps make the project's data landscape visible. That matters because research data decisions are often spread across proposals, ethics applications, Sikt notifications, data agreements, storage folders, consent forms, README files, and individual memory. The inventory gives the project one place to see how these pieces connect.

## What the inventory does

A data management plan describes intentions: how the project plans to handle data. The inventory records the data objects those intentions apply to. It is closer to the project's working reality.

The inventory helps answer questions such as:

- What data objects will the project create, collect, receive, or derive?
- Which objects contain personal data, sensitive material, or contextual risk?
- Where is the authoritative copy stored?
- Who has access?
- Which objects are covered by consent forms, Sikt notification, agreements, or other restrictions?
- Which objects need documentation, such as a README, codebook, or processing note?
- What should be deleted, retained, archived, restricted, or shared?

The point is not to document everything for its own sake. The point is to support decisions while the project is still active enough to act on them.

## What the inventory is not

The inventory is not a list of every file. A project with twenty interview transcript files usually does not need twenty inventory rows if the files have the same storage location, access conditions, sensitivity, documentation, and retention plan.

The inventory is also not a full metadata catalogue. Detailed variable descriptions, interview logs, file naming rules, transcription notes, and codebooks may live in other documents. The inventory should point to them where relevant.

## When to start

Start early. At the proposal stage, the inventory can be a sketch: expected data objects, likely sensitivity, likely responsibility, and open questions. Before collection, it should become more concrete. During collection and analysis, it should reflect what actually exists. At project closure, it should record what was archived, deleted, retained, transferred, or shared.

The inventory does not need constant attention. Update it at project milestones:

| Moment | What to update |
| --- | --- |
| Project design | Add expected data objects and obvious risk or restriction questions |
| Funding application or DMP | Add planned storage, responsibility, access, retention, and sharing intentions |
| Data collection starts | Confirm actual storage and access |
| Mid-project review | Add new objects, update status, resolve unknowns |
| Data processing or analysis | Add derived objects when handling decisions change |
| Project closure | Record deletion, retention, archiving, sharing, or transfer outcomes |

## Key idea

A useful inventory is specific enough to guide responsible handling, but small enough that the project will actually maintain it.
