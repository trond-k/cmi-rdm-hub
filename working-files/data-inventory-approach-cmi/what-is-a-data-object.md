# What is a data object?

A data object is a meaningful unit of research material that can be described, assessed, managed, and followed over time.

It may be a dataset, a group of files, a folder, a documentation package, a collection of consent records, a set of transcripts, a codebook, an analytical file, or a derived version of earlier data.

The useful question is not "is this really one object?" The useful question is:

> Does this material need its own decisions about storage, access, responsibility, documentation, retention, sharing, or deletion?

If yes, it probably deserves its own inventory row.

## Why data objects help

Many CMI projects contain several kinds of material: recordings, transcripts, fieldnotes, survey exports, contact lists, partner datasets, code, reports, documentation, and derived analytical files. These do not all need the same handling.

Thinking object by object makes the decisions smaller and more honest. Instead of asking whether "the project data" can be shared, the project can ask:

- Can the raw survey export be shared?
- Can the de-identified analytical dataset be shared?
- Can the codebook be shared?
- Can the analysis scripts be shared?
- Should the contact list be deleted?

The answers may differ, and the inventory should make those differences visible.

## Common data objects

Common CMI data objects include:

| Data object | Example |
| --- | --- |
| Interview recordings | Audio files from recorded interviews |
| Interview transcripts | Written transcripts produced from recordings |
| Fieldnotes | Notes from observation, informal conversations, or fieldwork |
| Focus group data | Recordings, transcripts, notes, or summaries from group discussions |
| Survey data | Raw export, cleaned dataset, analytical dataset, or codebook |
| Administrative data extract | Data received from an authority, organisation, or partner |
| Social media or digital trace data | Posts, comments, metadata, timestamps, network data, screenshots |
| Consent documentation | Consent forms, oral consent records, information sheets |
| Recruitment records | Contact lists, invitation logs, sampling lists |
| Code and scripts | Files used to clean, analyse, transform, or visualise data |
| Documentation | README files, codebooks, metadata records, method notes, processing logs |
| Derived data | Pseudonymised, anonymised, aggregated, coded, or transformed versions |

## Transformations can create new objects

Data often changes form during research. An interview recording becomes a transcript. A transcript may become a pseudonymised transcript. Survey responses become a cleaned dataset. A cleaned dataset becomes an analytical dataset. An analytical dataset may become a restricted or public replication package.

A transformation should create a new inventory row when it changes the management conditions of the material.

For example:

| Source object | Derived object | Why this may matter |
| --- | --- | --- |
| Interview audio recordings | Pseudonymised transcripts | Different identifiability, storage, access, and retention |
| Raw survey export | De-identified analytical dataset | Different sharing and archiving possibilities |
| Partner data extract | Derived indicators | Different contractual or disclosure conditions |
| Fieldnotes | Anonymised publication excerpts | Different review and publication pathway |

Not every version needs a new row. A typo correction or unchanged file copy does not normally create a new object. A new row is useful when the handling decision changes.

## Key idea

A data object is the level at which a project can make a practical decision. If the same answers apply to the whole thing, keep it together. If different answers are needed, split it.
