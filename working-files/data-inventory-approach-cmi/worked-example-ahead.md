# Worked example: AHEAD

This worked example uses the AHEAD project to test the CMI starter inventory against a real, complex project. It is based on the technical stress-test in `../data-inventory-approach/examples/worked-example-ahead.md`, but this version is written for the researcher-facing Hub.

It is not an official project record. Several entries use `TBD` because the source material described the project before fieldwork and before all approvals, agreements, storage locations, and data-management decisions had been finalised.

Snapshot date: 2026-04-24. At this point the project has started, but fieldwork is planned for Q4 2026. Most data objects are therefore still planned rather than live.

## Why this is a useful test case

AHEAD is a good stress test because it has many features that are common in CMI research, but rarely simple in data-management terms:

- international collaboration between CMI and the University of Zambia
- health-related research data
- two field sites with different political, environmental, and institutional contexts
- interviews, observation, household surveys, workshops, and secondary data
- participant-produced photos, drawings, diagrams, and audio
- public-facing outputs, including an online community map
- possible cross-border data transfers and partner agreements
- open-science ambitions alongside sensitive contexts

The example shows why the inventory should be small enough to use early, but flexible enough to flag where more detail is needed.

## How the inventory changes over time

At this snapshot, many entries are allowed to be incomplete. That is not a failure. The value of the inventory is that it shows what must be clarified before fieldwork and before publication.

Before fieldwork starts, the project should update:

- approval references and dates
- Sikt reference and status
- data agreements and transfer arrangements
- actual storage locations
- who has access to each restricted object
- participant information sheet versions and languages
- whether raw survey data, recordings, fieldnotes, and mapping media need separate handling by site or participant group

During fieldwork, planned rows become live rows. Some broad rows may need to split. For example, "fieldnotes across sites" may become one row per researcher or per site if access, responsibility, or sensitivity differs. "Collaborative mapping media" may need to split by site, media type, or participant group if different permissions or publication pathways apply.

During analysis, derived rows become more important. The cleaned survey dataset, pseudonymised transcripts, SAE estimates, and online community map all need separate rows because their access, sensitivity, documentation, and sharing possibilities differ from their source materials.

At project closure, the inventory should record what was deleted, retained, archived, transferred, published, or restricted.

## Optional detail this project would need

The starter inventory is enough to begin, but AHEAD clearly triggers several optional field groups.

### GDPR and personal data follow-up

Add detail for raw survey responses, interview recordings, transcripts, recruitment records, fieldnotes, collaborative mapping media, workshop notes, and possibly district medical office data.

Useful extra fields include:

- personal data status
- identifier types
- special category data
- contextual identifiability
- lawful basis
- Sikt relevance

### Ethics and contextual risk follow-up

The inventory should record why some objects are sensitive, not just that they are sensitive. Plantation workers, health workers, residents in polluted zones, and institutional actors may face different risks.

Useful extra fields include:

- participant or data subject group
- country or site
- risk notes
- ethics conditions
- reuse limitations

### Partner and agreement follow-up

AHEAD involves both a project partner and external data providers. These are different relationships and should not be collapsed into one note.

Useful extra fields include:

- partner or provider
- partner responsibility
- agreement reference
- transfer method
- contractual restrictions

This matters especially for ZAMPHIA, census data, district medical office data, and any CMI-UNZA transfer of personal data.

### Documentation follow-up

The project will need documentation for several derived or reusable objects:

- survey instrument
- survey codebook
- cleaning and analysis scripts
- small-area estimation method notes
- transcription and pseudonymisation notes
- collaborative mapping curation and anonymisation policy
- README for any archive or replication package

### Sharing and archiving follow-up

The project has open-science ambitions, but not all data objects can travel. The inventory should separate:

- objects that may be openly shared, such as the survey instrument or some aggregate outputs
- objects that may be shared only under restriction, such as de-identified analytical data
- objects that should not be shared, such as raw recordings, contact records, raw mapping media, or sensitive fieldnotes
- public-facing derived artefacts, such as the online community map, which require specific disclosure review

### Closure and deletion follow-up

Short-lifespan or high-risk objects need explicit end points:

- recruitment and contact records
- raw interview recordings
- temporary transfer copies
- pseudonymisation key
- raw collaborative mapping media
- raw or identifiable survey exports

## Outputs: what belongs in the inventory?

AHEAD plans journal articles, public-facing pieces, policy outputs, a CMI project website, an online community map, and other dissemination activities.

Not all outputs are data inventory rows.

| Output | Inventory treatment |
| --- | --- |
| Journal articles | Usually not data objects; track through normal publication systems |
| Policy paper | Usually not a data object; track as project output |
| The Conversation or similar public pieces | Not data objects unless they contain data-bearing material needing governance |
| CMI project website | Usually an output or communication channel, not a data object |
| Online community map | Data-bearing derived artefact; include in the inventory |
| Public aggregate dataset or replication package | Include in the inventory if it contains data, code, documentation, or access conditions |

The rule is practical: if the output contains or hosts research data, code, documentation, participant-produced material, or a reusable data product, it belongs in the inventory. If it is a narrative publication, track it elsewhere and link it only if useful.

## What this example shows about the starter model

The 12-field model works as a front door. It gives enough structure to see the project data landscape before fieldwork begins.

It also shows where optional detail becomes necessary:

- `Source or method` must distinguish created, received, contributed, collected, and derived material.
- `Personal data and sensitivity` should allow both legal sensitivity and contextual risk.
- `Legal, Sikt, or restriction note` should work as a pointer to obligations, not as the full legal analysis.
- `Status` can stay simple if "Planned" and "To be reviewed" are used honestly.
- Derived objects should have their source objects represented somewhere in the inventory.
- Public-facing derived artefacts need their own rows when they have a different access and risk profile from the source data.

The most important lesson is that the inventory is useful even while incomplete. At this stage, it does not settle every decision. It shows which decisions the project must settle before data collection, analysis, publication, archiving, or deletion.
