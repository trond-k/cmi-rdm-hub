# Choosing the right level of detail

The inventory should describe data at the level where meaningful decisions can be made. If the object is too broad, important differences disappear. If it is too narrow, the inventory becomes hard to maintain.

The aim is simple: specific enough to guide responsible handling, broad enough to remain usable.

## Start from the decision

A broad object is acceptable when the same main decisions apply to all the material. A more specific object is needed when different parts require different storage, access, documentation, retention, sharing, or deletion decisions.

For example, "interview data" is usually too broad if it includes recordings, transcripts, consent records, contact lists, and anonymised publication excerpts. These materials differ in identifiability, access conditions, storage needs, and future use.

A better breakdown might be:

- interview audio recordings
- interview transcripts
- pseudonymised transcripts
- consent records
- recruitment and contact records
- anonymised excerpts for publication
- interview documentation and README files

This does not mean every file needs an inventory row. It means materials should be separated when they need different handling.

## When to group material

Group material into one data object when the same answers apply to the whole group.

Grouping is usually appropriate when the material shares:

- source or method
- sensitivity level
- personal data status
- storage location
- access conditions
- responsibility
- documentation needs
- retention plan
- sharing or archiving outcome

Examples:

| Grouped object | Why grouping works |
| --- | --- |
| Pseudonymised interview transcripts, work package 2 | Same method, access level, storage, and retention plan |
| Fieldnotes from country A | Same fieldwork period, responsibility, and access restrictions |
| Analysis scripts for article 1 | Stored together and documented as one analytical package |
| Baseline survey documentation | Codebook, questionnaire, and README can be managed together |

## When to split material

Split material when one part needs different handling from another.

Useful reasons to split include:

- one part contains direct identifiers and another does not
- one part is more sensitive than another
- different people or organisations are responsible
- different parts are stored in different systems
- access should be limited differently
- some material can be shared while other material cannot
- some material should be deleted while other material should be retained
- one version is raw and another is cleaned, anonymised, aggregated, or prepared for publication
- different documentation is needed to understand or reuse the material

Examples:

| Too broad | Better split |
| --- | --- |
| Interview data | Audio recordings, transcripts, pseudonymised transcripts, consent records, publication excerpts |
| Survey data | Raw export, cleaned dataset, de-identified analytical dataset, codebook, scripts |
| Fieldwork material | Fieldnotes, photographs, consent records, contact lists, analytical memos |
| Partner data | Original extract, working copy, derived indicators, agreement or restriction note |
| Project files | Data files, documentation files, consent files, analysis scripts, outputs |

## Practical test

Ask whether the same answer applies to the whole object:

- Does it have the same sensitivity level?
- Does it have the same personal data status?
- Is it stored in the same place?
- Should the same people have access?
- Is the same role responsible?
- Does the same retention plan apply?
- Does the same sharing or archiving decision apply?
- Can the same documentation explain it?

If the answer is mostly yes, one row is probably enough. If the answer is no for several questions, split the object.

## Key idea

Use the smallest number of rows that still preserves the decisions that matter.
